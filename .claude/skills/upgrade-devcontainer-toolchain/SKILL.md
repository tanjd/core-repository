# Upgrading the devcontainer toolchain

The devcontainer pins tool versions in two files that must move together:
`.devcontainer/devcontainer.json` (`features` block — the source of truth,
hand-edited) and `.devcontainer/devcontainer-lock.json` (feature image
digests — derived, regenerated by a container rebuild, never hand-edit it).

Several other files hardcode a version read from `devcontainer.json`, or
copy one by convention, and don't update themselves when it changes — the
bulk of this skill is grepping for every one of those after the bump.

## 1. Bump `.devcontainer/devcontainer.json`

Check each feature's latest version/tag before bumping (its GHCR feature
page, or `devcontainer features info tags <feature-id>` if the CLI is
available). Features currently pinned:

- `ghcr.io/devcontainers-extra/features/pre-commit` — pre-commit version
- `ghcr.io/devcontainers/features/docker-in-docker` — feature tag _and_ the
  `version`/`dockerDashComposeVersion` options
- `ghcr.io/devcontainers/features/python` — feature tag = Python version
- `ghcr.io/va-h/devcontainers-features/uv` — uv version
- `ghcr.io/devcontainers/features/node` — feature tag, plus `pnpmVersion`
  (the single source of truth for pnpm everywhere else in the repo — see
  step 3) and `nvmVersion`
- `ghcr.io/devcontainers/features/go` — Go version and `golangciLintVersion`
- `ghcr.io/devcontainers/features/github-cli` — gh CLI version

A feature's major/minor tag (e.g. `node:1` → `node:2.1.0`) is part of the
JSON _key_ itself, not just a `version` field inside it — that key string is
what step 3 needs to grep for, not just the version number.

## 2. Rebuild the container to regenerate the lockfile

**Manual step — the user has to do this, Claude Code can't trigger it.**
Claude Code is running _inside_ the devcontainer, so it has no way to tear
down and rebuild the very container it's running in. After editing
`devcontainer.json`, stop and ask the user to run **Dev Containers: Rebuild
Container** in VS Code; `devcontainer-lock.json` regenerates automatically
as part of that rebuild — never hand-edit it.

Don't proceed to step 3 until the user confirms the rebuild finished and
the container came back up on the new versions — propagating a version
before the rebuild confirms it actually resolves risks propagating a bad
one.

## 3. Propagate the version bump

Once the rebuild confirms the new values (`git diff .devcontainer/`), grep
the repo for anything still referencing the _old_ ones — including, for
Node, the old feature key string embedded in a `jq` path:

```bash
grep -rn "<old node feature key>" --include="*.yml" .github/
grep -rn "pnpm@<old pnpm version>" apps/*/Dockerfile
grep -rn "python:<old py>-slim" apps/*/Dockerfile tools/generators/telegram-bot/files/
grep -rln 'requires-python = ">=<old py>"' apps libs tools
grep -rn "py<old py, no dot>" ruff.toml
grep -rn "Python <old py>\|golangci-lint <old version>" README.md CLAUDE.md
```

Known touch points from past bumps (re-confirm before trusting this list —
apps get added/removed over time):

- `.github/workflows/{ci,publish,release}.yml` — all three read
  `pnpmVersion` out of `devcontainer.json` via the same `jq` one-liner keyed
  on the node feature's full `features["..."]` string; the key must match
  exactly or the step silently produces `null` instead of erroring.
- Every deployable Next.js app's `Dockerfile` (currently `bookshelf`,
  `ledger-lens`) — `corepack prepare pnpm@<version>` is **hardcoded twice
  per file** (deps + builder stages), because `.dockerignore` excludes
  `.devcontainer/` from the build context. A comment above each line says to
  keep it in sync; nothing enforces that automatically.
- Every Python app's `Dockerfile` (`index-watch`, `otobr-buddy`,
  `table-talks`, plus the generator's `Dockerfile.template`) —
  `FROM python:<version>-slim` appears **twice per file** (builder + runtime
  stage).
- Every Python app's `pyproject.toml` (same four, plus
  `libs/telegram-bot-shared/pyproject.toml`) — `requires-python`.
- Root `ruff.toml` — `target-version = "py<NN>"`.
- Root `README.md` and `CLAUDE.md` — prose mentions of the Python/Go/
  golangci-lint versions. Cosmetic, but worth catching in the same commit
  rather than leaving docs to drift.
- `package.json` / `pnpm-workspace.yaml` — only relevant if the pnpm
  _major_ moved and it changed where non-registry pnpm config lives (pnpm 11
  moved `pnpm.onlyBuiltDependencies`/`pnpm.overrides` out of `package.json`
  entirely into `pnpm-workspace.yaml`'s `allowBuilds`/`overrides` keys —
  `git log -p -- package.json pnpm-workspace.yaml` around that bump shows
  the shape of that migration if it recurs for a future pnpm major).

## 4. Regenerate lockfiles for a Python version bump

Each affected app's `uv.lock` pins wheels per Python version — regenerate
after bumping `requires-python`:

```bash
for app in index-watch otobr-buddy table-talks; do
  (cd apps/$app && uv lock)
done
(cd libs/telegram-bot-shared && uv lock)
```

A pnpm major bump doesn't require touching `pnpm-lock.yaml` by hand — a
normal `pnpm install` (already part of `make setup`/CI) handles it.

## 5. Verify and commit

```bash
make affected   # nx affected -t lint test — closest to what CI's gate runs
```

This lands as one commit even though it touches ~25 files across every
app — it's a single coordinated version bump, not several unrelated
changes. Use the `commit` skill to draft and create it.
