# CLAUDE.md

Guidance for `apps/otobr-buddy` specifically — see the repo-root `CLAUDE.md` for cross-cutting
conventions (Nx, Python/uv tooling, deployment, release process).

Telegram bot that supports a church's one-to-one Bible reading ministry. Migrated from the
standalone `tanjd/otobr-buddy` repo (squash-imported, no preserved history), same
`src/otobr_buddy/` nested-package layout and `uv` + `nx:run-commands` pattern as
[[index-watch]]/[[table-talks]]. Adapted beyond the standard cross-cutting treatment:

- Dropped its own `health.py` and the token-selection logic in `config.py` in favor of
  `libs/telegram-bot-shared` (`start_health_server`, `select_bot_token`/`require_bot_token`,
  `configure_logging`) — the standalone repo predated that shared lib and had reimplemented all
  three nearly verbatim.
- **Pairing flow reworked**: the standalone repo's only pairing mechanism was a DM invite-code
  handshake (`/invite` generates a code, the partner DMs `/join <code>`), which in practice
  people struggled to complete — it requires both sides to already be in a private chat with the
  bot and to copy a code correctly out-of-band. Added `/pair`: add the bot to a group chat shared
  with your reading partner, both send `/pair` there, and the first two distinct senders become
  partnered with that group set as `group_chat_id` — no code exchange. Backed by a new
  `pending_pairs` table (`group_chat_id` PK, `claimant_id`, `expires_at`; 24h TTL, same shape as
  `invites`). `/invite`+`/join` are kept as a DM-only fallback for pairs who don't want a shared
  group — enforced via `_require_private_chat` (`bot.py`), which also gates `/partners` and
  `/history` since both list _all_ of a user's partnerships/history, not just the one tied to the
  current chat, and would otherwise leak a partnership into a group it has nothing to do with.
  `/log`/`/setfrequency`/`/stats`/`/end` stay unrestricted since a partnership's `group_chat_id`
  makes running them in the linked group the intended flow. `/link` (attaches a group to an
  already-DM-paired partnership) gained a guard against
  double-linking a group that's already tied to a different active partnership — a gap that
  existed in the original code and would otherwise let two partnerships silently collide on the
  same `group_chat_id`, with reminders/`/log` going to the wrong pair.
- Added `tests/test_bot.py` and `tests/test_reminders.py` — the standalone repo had zero coverage
  on command handlers or `JobQueue` scheduling (only `config.py`/`database.py`/`stats.py` were
  tested), despite those being the riskiest, most user-facing logic.
- Added an admin-only `/debug` command (`database.get_db_stats()` — total users, active/ended
  partnerships, total sessions) gated on `Config.admin_chat_ids`, matching `index-watch`'s
  existing `/debug` pattern. The `ADMIN_CHAT_IDS` env parsing and the `chat_id in admin_chat_ids`
  check were pulled out of `index-watch` into `telegram_bot_shared.env`
  (`parse_admin_chat_ids`/`is_admin`) so both bots (and any future one) share it instead of each
  reimplementing the same `os.getenv("ADMIN_CHAT_IDS", "").split(",")` logic — `index-watch`'s
  `config.py`/`bot.py` were refactored onto the shared helpers in the same change. An empty/unset
  `ADMIN_CHAT_IDS` leaves the command unrestricted (matches `index-watch`'s existing opt-in
  behavior, not a new default).

Ruff's `src` setting (which does not propagate through the shared root `ruff.toml`'s `extend`)
is `["src", "tests"]` here, matching the generator template's package layout.

`CHANGELOG.md` was seeded with the standalone repo's pre-migration history (single "Initial
Release" entry, `python-semantic-release` tag format `v{version}`) so changelog continuity
survives the migration; `nx release` prepends new entries above it. Nothing in this app reads
`CHANGELOG.md`/`package.json` at runtime.

Dockerized (GHCR) and versioned independently via `nx release` (`release.projects` in root
`nx.json`).

## Core concepts

- **User** — a Telegram user known to the bot once they've interacted with it.
- **Partnership** — a link between two users who read together. Has a status
  (`active`/`ended`), a reminder frequency mode, and may be associated with a group chat
  (optional) in addition to the two users' DMs. A user can have multiple active partnerships
  simultaneously (e.g. reading with one person while mentoring another).
- **Session** — one logged instance of a reading meeting: a free-text description of what was
  covered, who logged it, and when.
- **Invite** — a short-lived DM-pairing code generated by one user for a partner to redeem
  (fallback path; see "Pairing flow reworked" above).
- **Pending pair** — a short-lived claim on a group chat by the first user to send `/pair`
  there, resolved into a partnership once a second distinct user also sends `/pair`.

## Data model

Raw `sqlite3` (no ORM), via `database.get_db()` context-manager pattern:

```
users(telegram_id PK, username, first_name, created_at)

partnerships(
  id PK, user_a_id, user_b_id, status,
  frequency_mode, frequency_interval_days NULL,
  frequency_day_of_week NULL, frequency_time NULL,
  group_chat_id NULL, started_at, ended_at NULL
)

invites(
  code PK, created_by, expires_at, used_by NULL, used_at NULL
)

pending_pairs(
  group_chat_id PK, claimant_id, created_at, expires_at
)

sessions(id PK, partnership_id FK, text_covered, logged_by, logged_at)
```

## Reminder scheduling

`python-telegram-bot`'s built-in `JobQueue` (APScheduler-backed) for both reminder modes:

- **Interval mode** — schedule/reschedule a one-off job for
  `last_session.logged_at + frequency_interval_days` each time a new session is logged.
- **Fixed schedule mode** — a recurring weekly job keyed to `frequency_day_of_week` +
  `frequency_time`.

All scheduled times use a single church-wide `TIMEZONE` env var (no per-user timezone). Reminder
delivery target: the partnership's `group_chat_id` if set, otherwise DM both users individually.
